# 戦利品画面の停滞修理と実機復帰

利用者の「止まってんぞ」「今止まってるんだから解決してよ」に対し、現在の停止を解消し、停滞の通知漏れを修理した。

## 原因と修理

`progress-flow014`は同じ`loot-wait`を約955秒観測していた。既知の待機規則では毎回未解決時間をリセットしており、静止していても通知にならなかった。プロセスは確認時点で終了していたが、正常終了結果とエラーログがなく、終了理由は未解明。

待機規則にも既存の複数回観測・10秒の画像変化停止判定を接続した。画像が変わる間は観測を続け、別の待機画面へ移れば猶予を与える。入力期限に達していなくても静止を通知し、自動再送はしない。停止アイコン優先と回復監視の250ms周期を維持した。

実画面では報酬の未開示アイテムが残っていた。製品`click-point`からNanoSerialHidで空白位置を1回クリックするとアイテムが開示され、自動着用・退出・次のエリアのボタンが現れた。単に待てば進む画面ではなかった。

現れた操作ボタンを拾えない原因は、戦利品見出しの探索範囲が狭く、退出ボタンの範囲も実際の配置から外れていたこと。実画像をfixtureに保存し、設定の探索範囲を修理した。自動着用確認窓も実際の見出しで認識し、背景の同名ボタンによる低優先規則の曖昧判定より、確認窓の規則を優先するよう修理した。

## 検証

- 修理前は、既知待機の静止通知2件と実画像の操作認識・確認窓認識が失敗し、修理後は成功。
- 最終のHost関連448件成功。進行focused34件成功。
- 正規開発版更新後、導入Host DLLとRelease成果物のSHA-256一致。
- 導入版の入力なし計測は、現在の戦利品に対して待機規則だけを持つ診断設定を15秒適用。通常設定は維持し、計測終了後は通常設定で再開した。

| 入力なし計測 | 実測 |
|---|---:|
| 進行観測 | 30回 |
| 最初の静止通知判断 | 開始11,150ms |
| 回復観測 | 59回 |
| 回復観測間隔の最大 | 285ms |
| ゲーム入力・AI呼出し | 0回 |

[計測記録](wait-stall-measure-events.jsonl)。通常設定での`progress-flow015`も10,831msで静止を検知し、写真付き決裁申請を自動作成した。これは実機の通知経路成立として記録し、調査継続中の重複確認は取り下げた。

## 実機結果と現在地

`progress-flow016`で自動着用をNanoクリックし、確認窓まで進んだ。修理後の`progress-flow017`は確認窓でSpaceを送出し、続いて自動着用規則のクリック、退出規則のクリックを記録。実画面でティルコネイルへの移動表示を確認した。[入力・通知記録](wait-stall-recovery-events.jsonl)。

その後、ボーナス選択を検出し、15,802msで入力を停止した。表示は「防御優先3段階」「速度優先1段階」「技巧優先1段階」で、写真と正しい3択を持つ決裁申請`K-WH2EJU`が自動作成された。回答先は現在の会話へ引き継いだ。ボーナスは自動選択していない。

現在の戦利品画面の停滞は解消済み。未知の全画面からの自律復帰、メインクエスト全体の完遂、旧プロセスの終了原因は未確認。入力の再開にはボーナスへの回答が必要。回復条件は上級ポーション70％・10秒待ち、包帯の白20％を維持する。
