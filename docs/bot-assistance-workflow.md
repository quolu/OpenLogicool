# Botの詰まりからAI支援を呼ぶ

## 承認済みの運用

Botは実行時間の上限を設けず、画面と入力・回復の観測を継続する。詰まりを検出してから1分間は、担当AIにもApproval Boxにも通知せず、既存の操作と観測を続ける。その間に復帰した時は通知せず、1分経過後も詰まりが続く時だけ最新の根拠を通知する。AIは常時監視や定期巡回をせず、Botが詰まった時だけ通知で起き、原因を考えて対応する。人の選択が必要な案件だけApproval Boxへ申請する。BotからAIを起こす通知を、人の回答待ちへ置き換えない。

画面の選択肢を担当AIが判断できない時は、具体的な候補と判明した事実・推測を会話とApproval Boxへ示し、回答まで選択を保留する。修理など回答に依存しない承認済み作業は続ける。

活動の自動選択は、明確な推奨表示と一意な移動先を確認できる場合だけとする。それ以外は待機して担当AIへ知らせ、判断できない場合は決裁箱へ出す。ボーナス等の選択は既存の回答方針で扱う。

ボーナスの選択表示は、Botが検出した回に決裁箱へ選択肢と画面を直接申請する。この申請は1分の待機と担当AIへの通知を経由しない。申請できなかった時だけ、1分後の詰まり通知が担当AIへ届く。回答が入ったら、Botは回答した時と同じ選択肢が表示されている間だけ選ばれたカードを押し、確定の表示を確かめてから確定キーを送る。Botが押すのは利用者が答えた選択だけで、回答のない選択と「入力を停止したままにする」の回答では何も押さない。回答どおりに進められない時は、根拠を添えて担当AIへ知らせる。

AIは `https://mabimoba.kitepon.dev/`、X、Webを情報源にする。保存画像・操作履歴・実測と外部攻略を照合し、未確認情報は未確認として扱う。役立つ攻略はベルチームのルピーへ根拠と一緒に渡し、サイト更新を依頼する。

対応は個別イベントやNPC名・クエスト名のハードコードを増やさず、対話の選択・必要品の不足・入手方法の確認・進行条件・操作結果の確認など、別の場面にも適用できる仕組みとして実装する。実装・focused test・開発版導入・実効確認・通常commit/pushまで続ける。API送出成功や項目選択をクエスト達成と扱わない。

Botの入力は、表示に応じた規則だけが送る。表示条件のない定期Spaceは送らない。右下コンパス、手入力優先と全解放後5秒（手入力はキーボード・マウスの移動とボタンとホイール・G13／G600など、人の手の入力装置すべて。Bot自身の入力は入力元の機器で見分けて数えない）、停止表示優先、毎秒4回の回復監視、HP70％のポーション・白20％の包帯を引き継ぐ。入力はNanoだけとし、別の出力方式や入力の自動再送へ切り替えない。クリックの前にマウスの矢印を動かせない時は、ボタンを押さず、Botを止めずに手入力があった時と同じだけ待って次の観測でやり直す。1分続いたら詰まりとして担当AIへ知らせる。Nanoが無応答なら物理抜き挿しを依頼せず、接続と所有者を確認し、承認済みのNano一台に限定したWindows標準機器再起動と正規診断を使う。通信復旧を根本原因の特定と扱わない。

シルバーコインは、左上の表示が30以下になったら、所持品の「小さなシルバーコインボックス」（1個を獲得する箱）を70個開けて補充する。箱の説明が1個の獲得であることと、数量の欄が70であることを読めた時だけ開封する。読めない・見つからない・進まない時は押さずに止まり、詰まりとして担当AIへ知らせる。補充の規則は補充の間だけ有効で、利用者が手で開いた所持品には触れない。

停止表示が止めるのは、Spaceを押す操作だけとする。Spaceを送らない操作（T・B・クリックなど）は停止表示中も送る。承認済みの休憩退出は、右下の料理・食事の両メニューを確認した時だけ停止表示より優先する。小さいSpace表記のOCRに退出を依存させない。停止表示中の静止も詰まり観測と1分の通知待機の対象にし、表示中という理由だけで通知対象から除外しない。画面が動き出した時は未通知の案件を破棄する。

## 機能

Botの動きは、機能ごとの部品に分けてある。メインのBotは、部品の組み合わせである。機能は単独でも、選んだ組み合わせでも動かせる。

```powershell
& $cli bot functions                                        # 機能の一覧と、メインに入っているか
& $cli bot start mabinogi-mobile                            # メインの組み合わせ（今までのBot）
& $cli bot start mabinogi-mobile --functions dialogue       # 会話を進める機能だけ
& $cli bot start mabinogi-mobile --functions recovery,dialogue,results
```

- 機能の規則は、進行設定（`progress.json`）の隣の`functions/<機能>.json`だけに置く。`progress.json`は、メインの組み合わせ（`Functions`）と、選んだ時だけ読む機能（`OptionalFunctions`）だけを書く。規則を足す時は、当てはまる機能のファイルへ足す。新しい機能は、ファイルを足して`progress.json`の一覧へ書く（一覧に無いファイル・ファイルの無い機能は、読込みで誤りとして止まる）。
- 回復（`recovery`）は規則ではなく監視の側の機能で、同じ並びで選べる。機能を選んで始めた時は、選ばなかった機能は回復も含めて動かない。
- 機能の並びは`progress.json`に書いた順で決まり、選ぶ順では変わらない（同じ優先度の規則の先後を変えないため）。
- モードは、そのモードを持つ機能を読み込んだ時だけ動く。指定なしで始めると、メインに、入っているモードの機能が足される。動いているBotが読み込んでいないモードは、次にBotを始めた時から動く。
- 設定（規則の位置・文字・条件）だけの直しは、導入先の`BotScripts/MabinogiMobile/`へ同じファイルを置いてBotを始め直せば効く（約10秒）。プログラムの直しは開発版の導入（約40秒）が要る。

## モード

モードは、利用者が担当AIへ言葉で伝えて切り替えるBotの動き方である。担当AIは導入版の入口でBotへ伝える。入ったモードは、解除するまで、Botとアプリを起動し直しても続く。

```powershell
& $cli bot modes            # モードの一覧と、入っているか
& $cli bot mode side-quest  # 「サイドクエストモード」と言われた時
& $cli bot mode off         # 「解除」と言われた時
```

モードの定義は進行設定（`progress.json`）の`Modes`と、そのモードの段階の規則だけに置く。Botが動いていれば次の観測から、止まっていれば次に始めた時から効く。解除した時は、モードが始めた段階をその場で終える。

## サイドクエストの受注

受注はメインの組み合わせに入っている機能（`side-quest`）である。通常のBotが右下のSpaceのボタンを押した直後（3秒以内）に「ミッションにチャレンジできる財貨が不足しています。」が出たら、受注の流れに入る。

1. 右の「クエスト＋」を押す。
2. 「サイド」を押す（選ばれていない時）。
3. 一番上のカードの真ん中を押す（カードが開き、「進行」のボタンが濃い緑になる）。
4. カードの内容（文字と画像）を実行の記録の`remembered/`へ残す。
5. 「進行」を押す。

受注した後は、通常の規則が続きを進める。`bot mode side-quest`は、通常の画面が2秒続いた時に同じ流れを1回始める。

- 進めない理由の知らせは1種類ではない。「今は不吉な召喚の結界がありません。出現するまで待機してください。」では受注に入らず待つ（利用者の裁定待ち）。Spaceの直後に見た画面と読んだ文字は、実行の記録の`after-check`と`after-check.png`に残る。
- 「クエスト＋」の帯は追跡中のクエストで地の色が変わる（緑・青・オレンジ）ので、帯の文字を拡大して読んで見つける。
- 「進行」は、同じ文字が縦に並ぶので、行ごとに読んで一番上の行を押す。まとめ読みのかたまりの中心は、ボタンの間に来る。
- 実機の位置と実測は[記録](../evidence/bot-side-quest-20261010/README.md)で読む。

## 規則に無い画面の判断（Jev）

Jevは、規則で決まらなかった画面にだけ使う、最後の汎用の判定である。クエストの情報（目的とカードの全文）を全部渡した上で、今の目的のために押す文字を選ばせる。名前や印で決まる選択は、Jevを使わず規則で行う。

Jevへ渡す止まりは2つ。規則にも通常の画面にも一致しない画面で止まった時と、判断へ渡すと指定した待つ規則（`Judge`。会話の選択肢）の画面で止まった時。

- 渡すのは、今の目的・目的の背景・画面から読んだ文字だけとする。クエスト・場所・画面の名前と、進め方の原則は、問いへ書かない。
- 画面ごとの規則が先に評価される。Jevでうまく選べない画面は、その画面の規則を機能のファイルへ足す。問いの文をその画面に合わせて書き換えない。
- 目的と背景は、覚える規則（`Remember`）の`GoalPrefix`で決める。覚えた行のうちその文字で始まる行が目的、覚えた行の全部が背景。サイドクエストは、受注したカードの「・」の行が目的になる。目的を覚えていない時は、Jevへ聞かない。
- 目的は2つの時に新しくなる。新しいクエストを受注した時は、カードの内容で覚え直す。同じクエストの目標が次へ進んだ時は、通常の画面の追跡中の表示（`Remember`の`Tracker`）から読み直す。覚えた名前が追跡中の名前（領域でいちばん大きい文字の行）に出ている時、その直ぐ下に詰めて並ぶ行が目標で、いちばん上の目標が変わっていたら目的の行だけを差し替える。同じ目標かは類似度0.5で見分け、続けて2回読めた時だけ書き換える。追跡中が別のクエストの時は読み直さない。
- Jevへ渡す文字は、Botの普段の読み取り（拡大と白い文字の読み直しを含む）とする。素の読み取りは、色の付いたボタンの文字を落とす。読み直しで同じ場所に重なった文字は、先に読めたほうを残す。
- 判断は2回の問いで行う。先に、文字ごとに「押して選ぶボタンの名前か」を聞いて選択肢を絞る（キーの名前・説明文・数値が落ちる）。次に、目的のために押すものを選ばせる。
- Botは、いちばん確率の高い答えを押す。「どれも押さない」が選ばれた時、選ばれた文字が画面に複数ある時、押す直前の画面に同じ文字が無い時、問い合わせに失敗した時は押さない。
- 聞くのは、止まった画面ごとに1回。画面が動いたら、次に止まった時に聞き直す。押しても画面が変わらない時は、今までどおり1分後に担当AIへ知らせる。同じ文字を2分のうちに3回押しても止まる時は、押さずに知らせる。
- 接続設定は、選択DBの隣の`bot-screen-judge.json`（鍵のファイルの場所とモデル）。置いていない時は、この判断を使わない。鍵そのものは設定・記録へ書かない。
- 渡した内容と選択肢ごとの確率は、実行の記録の`screen-judge`と、止まりのフォルダーの`screen-judge-*.json`に残る。

保存した画面で判断を確かめる時は、ゲームと入力装置に触れない入口を使う。`--background`は、目的の背景を1行ずつ書いたファイル。`--client-bounds`は、画像の中の描画領域（画面を撮った時の記録の`ClientBounds`）。

```powershell
& $cli game-index judge-image --image <画面.png> --settings "$env:USERPROFILE\.openlogicool\bot-screen-judge.json" `
    --goal '<目的>' --background <背景.txt> --progress-profile <progress.json> --client-bounds 1,31,1711,1085
```

### 会話の選択肢

会話の選択肢（上に相手の吹き出し、下に選択肢のボタン）は、次の順で決める。

1. 受注したクエストの名前と同じ選択肢が1つあれば、それを押す（`side-quest-talk`。覚える規則の1行目が名前）。
2. 「！」の付いた選択肢が1つあれば、それを押す（`dialogue-marked-choice`）。「！」は、ゲームが用件のある選択肢に付ける印。
3. どちらも無ければ押さずに待ち、止まったらJevへ渡す（`dialogue-choice-wait`の`Judge`）。Jevが「どれも押さない」を選んだ時と、目的を覚えていない時は、押さずに担当AIへ知らせる。

報告の相手との会話では、選択肢がクエストの名前だけで、目的の言葉（「報告」など）は画面に出ない。Jevは目的とカードの全文を渡しても選べなかった（3回とも「世間話」約0.5、クエストの名前は0.10）。このため、名前と印は規則で拾う。

## Throughline後の継続

新しい会話は本書、作業tree、直前の受入記録、Botの状態、未処理の通知を確認する。完了済みの操作を繰り返さない。現在の担当AIが通知先へ登録し直し、旧会話から新会話への配達切替を実測する。会話IDなどの変動値は製品が所有する構造化設定へ置き、規範文書やBotのイベント処理へ埋め込まない。

Throughlineで会話が切り替わるたびに、Botの通知先、ルピーとの通話、Approval Boxの回答先を新しい会話へ引き継ぐ。Approval Boxは`list_my_decisions`で引き継ぐ未決・保留の申請を確認し、申請ごとに`resume_decision`を呼んで回答先を変更する。新しい申請を重複して作らない。回答済みの操作は、直前の実測と完了状態を確認して繰り返さない。会話内で直接回答された申請は、その回答に従って実行し、理由を記して取り下げる。引き継ぎ後は各通知先と未処理案件を確認し、構造化した引き継ぎ状態へ保存する。

会話をまたぐ担当・通話・返答待ちは[引き継ぎ状態](bot-assistance-handoff.json)で読む。ルピーとの連絡はCall Bridgeの正規通話を使い、返信のポーリングや待機ループを作らない。`call_open`は新しい通話を作るため、移動時は新しい会話で通話を開き、旧通話へ移動先を知らせ、新通話へ返答待ちを渡してから旧通話を閉じる。

詰まりの識別子、実行と根拠画像、直前の送出、担当、返信先、対処状態を引き継ぐ。未処理の案件を消したり、配達結果が不明な通知を黙って再送したりしない。Throughlineの私有データやフックへプロジェクトの状態を書き込まず、製品の明示的な連携入口で宛先を更新する。

## 接続と案件の操作

担当にする会話（CodexまたはClaude）の標準shellで、導入版の入口を呼ぶ。

```powershell
$cli = './artifacts/development/OpenLogicool/OpenLogicool.Host.exe'
& $cli assistant attach
& $cli assistant status
& $cli assistant claim <案件ID>
# 原因・対処・実測結果を確認してから閉じる。
& $cli assistant resolve <案件ID> --reason '修理と実機確認の結果'
```

`attach`は呼び出した会話を担当に登録する。会話の種類は環境から決まる（`CODEX_THREAD_ID`があればCodex、`CLAUDE_CODE_SESSION_ID`があればClaude）。両方ある時だけ`--harness codex|claude`で指定する。一つの操作で未処理案件と担当を返し、引き継ぎ前の会話を退役させる。新しい会話は返された未処理案件を引き受ける。旧会話から再登録・claim・resolveすることはできない。Botを再起動せず、以後の詰まりの通知先が切り替わる。宛先は登録した1会話だけで、CodexとClaudeへ同時には送らない。

利用者が以前の会話へ直接戻って新しい作業を依頼した場合だけ、`assistant attach --takeover`で現在の担当を明示的に引き継ぐ。未処理案件と根拠は保持する。古い自動通知を受け取っただけの会話はこの指定を使わず、通常の退役拒否を守る。

Codexの会話への配達はAiterm 0.56.0以上の正規入口`aiterm-parent-delivery`を使う。導入・設定は公式の`npm install --global aiterm-mcp`と`aiterm-setup`で行う。`assistant attach`と送信前に、宛先とAitermのCodex差し込みが有効であることを検証する。未導入・宛先検証失敗・差し込み無効は明示エラーになり、キューだけの配達へ切り替えない。フックとCodexとの配達方言はAitermが所有し、OpenLogicoolは公開入口だけを呼ぶ。独自の定期起動は行わない。動作中の会話への通知は同じターンへ入り、待機中なら同じ会話の新しいターンになる。受付と実際の受信は分けて確認する。

Claudeの会話への配達は、その会話の受信箱へ1通書く。受信箱の方言は公開部品`aiterm-steer-delivery`（0.1.13以上・npmのglobal）の`sendClaudeInbox`が所有し、OpenLogicoolはその関数だけを呼ぶ。`attach`は宛先確認の文を1通送り、書き込めた時だけ登録する。確認の文がその会話へ届くことを担当AIが見て確かめる。受信箱の鍵は状態の隣の`inbox-target.json`だけに保存し、状態・出力・ログ・gitへ出さない。Claudeのアプリの再起動や会話の作り直しで宛先は無効になり、送信は明示エラーになる。その会話で`attach`をやり直す。

受信箱への送信は、会話が読んだことを通信では確かめられない。担当AIの`assistant claim`を受領の印にする。通知を受けた担当AIは、調査より先に`claim`する。

担当AIへ送れなかった時と、送ってから5分たっても担当AIが引き受けず画面も回復していない時は、Botが決裁箱で利用者へ「担当AIへBotの詰まり通知が届いていません」と知らせる。Botは案件が未処理の間、その申請の回答を読む。「担当AIへもう一度送る」と答えると、同じ通知を現在の担当へ送り直す。送り直しも届かない時は、その旨をもう一度知らせる。画面が回復したら、未回答の知らせを取り下げる。決裁箱の接続設定が無い時は、知らせの失敗を案件の`error`へ残す。

状態は選択DBの隣の`.bot-assistance/state.json`に製品が保存する。案件ID、根拠の場所、担当、配達受付ID、対処結果、利用者への知らせの申請IDを保持する。`open`は未処理、`claimed`は担当が対応中、`resolved`は対処済み。配達の`queued`は受付済み、`written`は受信箱へ書き込み済み、`failed`は失敗、`unknown`は結果不明であり、読了や修理完了を意味しない。`sending`のままprocessが終了した場合も状態を確認し、自動再送しない。

同じ詰まりの継続は、同一の根拠フォルダーの案件へ最新根拠を保存し、通知を連打しない。別の根拠フォルダーの詰まりと、画面復帰後の新しい詰まりは、古い案件が未処理でも別件として1回配達する。古い案件の根拠・担当・配達結果は保持する。画面が回復しても案件は消さず、`observedCleared`として記録する。担当が原因・結果を確認して閉じる。利用者の明示停止は通知の対象にせず、同じ案件の配達失敗・結果不明を自動再送しない。ゲーム入力の別方式への切替や自動再送も行わない。

Botの詰まりと異常終了は担当AIへ通知する。担当AIが画像と状況を調査し、人の選択が必要な時だけ具体的な選択肢を会話とApproval Boxへ出す。通知処理は進行と回復監視を待たせず、配達失敗もログへ表示する。
