# 録画の確認後に次の手順へ進めない

## 発生と原因

利用者から「手順9の次が提示されなかった」と報告された。実行 `exploration:58d60bfebb0f4a6fabf41c5e34efb623` では手順1〜8のAcceptを保存した後、手順9の入力前に停止した。次の画像はFreshnessMsが4,913で、許容1,000msを超えていた。終了欄は空で、終了手順の指定による停止ではない。

WGCの取得アダプタは、確認待ちの間にたまった古い画像をそのまま返していた。静止時に再利用するcacheも受信後の経過時間を加算していなかった。古いqueue画像を返す動作をfocused testで再現し、期限内の画像が届くまで取得処理で待つよう修理した。期限は探索policyと共有し、cacheには受信後の単調時間も加算する。新しい画像が来ない場合は取得timeoutで明示停止する。入力の再送、別capture方式への切替、期限の拡大は行わない。

この修理を導入した実行 `exploration:135841f0150c46219aa4a39d07832dc0` では手順9を実行し、結果画像の確認窓からAcceptを受領した。その後、手順10の入力前に「未調査の許可候補がありません」で停止した。次の画像のFreshnessMsは0だった。

手順9の観測がUndeterminedだったため、target discoveryがAI修復状態へ移っていた。録画再生はAI無効なので、その状態では保存済み手順10の候補も返さなかった。ユーザーのOKを受けても次へ進めない状態遷移が原因。AI無効の実行では非遷移の観測からAI修復状態へ移さないよう修理した。観測のUndetermined、原本、ユーザーのAcceptはそれぞれ保持し、Movedへ読み替えない。AI有効の探索の修復動作は維持する。

## 検証と導入

- 確認済み: 古いqueue画像の拒否、確認待ちによるcacheの期限切れ、期限内の画像が来ない場合のtimeout、policyとの期限一致を検証した。
- 確認済み: 前の観測が非遷移でも、AI無効の次の保存操作を返すことを検証した。修理前は次のクリック候補が0でテストが失敗した。
- 確認済み: 変更に直結する23件、最終のHost関連371件が通過した。失敗・skipは0。通し試験はこの個別修理で再実行していない。
- 確認済み: OpenLogicoolを正常終了し、正規の開発版installerで両修理を導入した。Host DLLのSHA-256はReleaseビルドと一致し、正規ランチャーから起動した。
- 確認済み: 原本298ファイルのhashは不変。記録session 8行、記録event 193行と、日課マクロの版1〜4を保持した。
- 未確認: 両修理を入れた最終版で、同じ実行の手順9のOK後に手順10の確認窓が出ること。Computer Useのwindow state取得が `foreground window did not report a process id` で再接続後も失敗したため、実機確認を続行できなかった。
