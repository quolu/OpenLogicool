# 保存済み操作デモの再解析

## 原因と修理

利用者が13:52に記録したNIKKE往復は、原本の画像・入力・取得時刻が保存されていた。画像の間引き修理後、独立DBの診断では両方Movedだったが、製品UIは古いUndeterminedの解析結果を表示していた。Host public intentsと記録画面に、保存原本を解析し直す入口がなかった。

記録画面へ「保存した記録を解析し直す」を追加した。元の記録と画像を変更せず、同じ`DemonstrationTimelineAnalyzer`で保存した時刻順に解析し、別のsessionへ結果を追記する。`SourceSessionId`と`ReanalyzedUtc`で元の記録と解析時刻を保持し、UIは「再解析済み」を表示して新しい結果を選択する。再解析結果をさらに解析する場合も、その元の記録原本を読む。

画像の所在から原本見出しを読み、選択した元sessionとの一致・形式0.4.0・停止情報を確認する。画像のSHA-256と寸法は既存の`DemonstrationRecordedFrameSource`で検証する。対象ゲームの新しい画面取得、Nano入力、SendInput、Computer Useによるゲーム入力を解析経路へ追加していない。

再解析は既存の記録・再生排他を保持する。進捗を表示し、終了後に既存のマクロ作成・再生・割当入口へ進む。原本のデータベース行、旧解析、旧route、旧revisionは更新しない。原本が欠ける場合やAIサービスが失敗した場合は、エラーを表示して停止する。

## Foundry Localの起動直後の誤判定

実UIの初回再解析で「Foundry Local serviceがreadyではありません」と停止した。`WindowsFoundryLocalRuntimeResolver`は`status`を取得した後に`model list`と`model load`を実行し、最初の状態で判定していた。

Windowsの公式CLIでサービスを通常停止し、`status`→`model list --loaded`→`status`を実行した。最初は`ready=false`・接続先なし、モデル一覧取得後は`ready=true`・接続先ありだった。モデル操作がサービスを起動するため、先に読んだ状態は実行時点の状態ではなかった。

resolverはモデル操作の後に実際の状態・接続先を取得するよう修理した。再試行・別providerへの切替・エラーの無視は追加していない。

## 検証

- 原本の全frameから新しい2操作の解析結果を生成し、旧Undeterminedの結果、入力、取得時刻、原本ファイルを保持した。SQLite再open後の一覧と、再解析結果から元の原本を再解析する経路も確認した。
- 他sessionの原本見出しを指す場合は拒否し、新しい結果を作らず排他を解放することを確認した。

## AI監視付き再生の早期終了

再解析を実UIで完了し、2操作とも「画面が変わった」と表示された。その結果から2手順・版1のマクロ「アークからロビー」を作成できた。

最初のAI監視付き再生は、ロビーにいることだけを根拠に操作0回で完了していた。実行結果`run-20261003-120152-965`に`ActionCallCount=0`と「現在すでにロビー画面のため、追加操作せず終了しました」が記録された。

原因は、選択した`InitialRoute`をCodexのroute recorderへ渡さず、目的名からrouteを探し直していたことと、新規学習と再生に同じ早期終了指示を使っていたことだった。合成マクロでは目的名から作るIDと選択したrouteのIDも異なるため、別のrouteへ学習する余地があった。

再生は選択したroute・版・手順列をそのままrecorderへ渡し、全手順の画面変化が成立した後だけ完了できるよう修理した。AIへの`observe`結果には`CanFinish`を返し、未完了の`finish`は明示エラーにする。再生用の指示は、目的名が現在画面に合っていても保存済み往復を実行する。新規学習の終了条件は維持する。

合成routeのIDを保持した2手順再生、途中完了の拒否、失敗した中間stepだけの修復と正常な前後step・旧版の保持、未実行の`finish`を成功表示しないことをfocused testで確認した。

## 記録した点座標と画像領域の混同

次の実UI再生`run-20261003-120652-079`では、保存actionの画像指紋取得が例外となった。2つの記録済みクリックはそれぞれ`[0.655732, 0.677314, 0, 0]`、`[0.074982, 0.940213, 0, 0]`で、点座標として正しく保存されていた。`CodexSuppliedTargetDiscovery`が面積のある領域を要求する`VisualPatchMatcher.Capture`へ点を渡したことが原因だった。

点座標は幅・高さを足さず、そのまま再生対象へ渡す。点には領域の画像指紋を付けず、面積のある既存候補には従来どおり付ける。保存原本・edge・座標を変更しない。実際の2点と画面端の点、既存の面積付き候補をfocused testで確認した。

この失敗では、tool例外の後にAIが新しいクリックを続け、画面は往復したがrouteには記録できなかった。実行またはroute保存の例外を、そのrunの入力停止として記録するよう修理した。既存routeがある場合も後続入力を送らず、再生成功にしないことを確認した。画面の実行状態も、Codex turnの`completed`とマクロの完了を区別して停止を表示する。

続く`run-20261003-121525-488`では、入力前の探索判定が点を拒否して停止した。`ExplorationCoordinator`と`NanoGameInteractionActions`も幅・高さが正数の矩形だけを受理していた。記録compilerの`demonstration-point`との不一致を、入力対象contractへ点と矩形の意味を明記して修理した。幅・高さが両方0の画面内の点だけを受理し、片方だけ0の線・範囲外・非有限値は拒否する。Observation・frame・transform・window照合は保持する。実録2点を元の位置へ一回だけ送ること、無効な対象と古いframeはdeviceを呼ばないことをfocused testで確認した。

## 記録区間を再生待機へ使った誤り

`run-20261003-122045-085`では、保存した1手順目をNanoで一回送信し、ロビーからアークへ実画面が変化した。保存した待機条件が5観測・安定1,444ms・上限3,359msだったため、実行時は4観測で時間切れとなり、`Undetermined`を保存した。AIは戻る操作で修復を試みたが、未解決の`OutcomeUnknown`を保持した既存のdispatch判定が次の入力を拒否して停止した。戻る操作のNano送信は行われなかった。

原因は`DemonstrationRouteCompiler`が原本の取得回数と操作間隔から再生待機を復元していたことだった。原本解析の短い因果区間と、live再生の10秒Compareは別の契約である。新しいデモ由来edgeは既存基盤と同じ2観測・安定1,000ms・上限10,000msを使う。既存の`demonstration|`を持つ保存edgeも、製品一手runtimeで同じ再生条件を使う。原本と保存edgeの古い実測値は更新しない。

短い記録区間から導出した往復、既存の5観測・3,359msのedgeを10秒Compareで再生することと保存値の不変をfocused testで確認した。

## アプリ専用設定と共通設定の保存名の衝突

両デバイスへマクロを割り当てる直前、NIKKEと共通設定がどちらも`ws-nikke`のprofileを参照していた。既存のアプリ専用workspaceへの分岐は、EXE名から同じ`ws-nikke`を提案し、共通設定を上書きする状態だった。

同名の共通workspaceを使う条件を実SQLiteの試験で再現した。専用workspaceの提案名が元の共通workspaceと同じ場合は`-application`を付け、保存先を分けるよう修理した。既存内容・LCD設定を継承し、専用設定の保存後も共通設定が不変であることを確認した。
